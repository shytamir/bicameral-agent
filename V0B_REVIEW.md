## Proposed scope and limits

| Item | Proposed value |
|---|---|
| Stage | v0b development only; v0c requires separate design and authorization |
| Allocation | At most 3 fresh Runs; A, C, B; trajectory seed 17; no replacements |
| Fixture | Simulated `api`, `database`, `worker`; no host, shell, Internet or arbitrary filesystem tools |
| Changes | R1 `set_config` and `restart`, only these resources; 24 mutating invocations per Run |
| Fixture actions | At most 40 total observations and mutations per Run; no snapshot restoration Grant |
| Tasks | Six fixed ticks, at most 8 Episodes per Run |
| Operator/common lane | At most 50 calls per Run, including 1 review and 1 closing reservation; at most 10 task calls per Episode |
| Steward task lane | A/C: at most 64 calls per Run; 2 consolidation attempts per Episode, at most 4 calls per attempt; B: none |
| Communication | Same separate finite allowance in every arm; either role's communication charges the common lane; cannot perform tasks, clear holds or replenish task allowances |
| Input/output per call | 24,576 context tokens, with 2,048 reserved for output; entire framed input counted before dispatch |
| Per-Run token ceilings | Operator/common: 1,228,800 input and 102,400 output; Steward tasks: 1,572,864 input and 131,072 output |
| Proposed input sections | Control 1,536; semantic 1,536; exchange 1,536; page 1,024; wake 512; framing margin 256 tokens |
| Time | 180 seconds per call; 45 minutes per Run; 135 minutes for all three Runs |
| Retry/recovery | No transport retry or repeat of an uncertain action; stop and review uncertain dispatch/recovery needs |
| Ending/disposition | Offer permitted reserved reporting, then dormant state; resumption intent UNDECIDED |
| Retention review | Within 30 days of last call; human decides a finite extension or justified removal; no automatic restart or deletion |

Limits intersect: 114 calls each consuming the full deadline cannot fit a 45-minute Run. Call counts are ceilings, not a promise to complete them. The elapsed limits, three-Run allocation and Grant mutation limit have not increased. Admission must preserve remaining communication time and tokens before each task call. Input-token ceilings conservatively allocate the full context size per call; unused budget does not expand a call's context. A/C receive the same semantic allowance; B uses ordinary evidence retrieval. Extra Steward costs must be reported explicitly.

The former 26-call cap allowed only 24 task calls against a 23-call idealized witness that omitted separate Commitment-wake work. It was not a calibrated allowance. On the revised harder fixture, the observation-based scripted solver uses 28 task calls, with per-task counts 5, 2, 7, 6, 6, 2. Conservatively reserving a separate wake read/outcome adds 2. Adding one invalid reply, one retrieval and one verification per task, then the two common communication calls, gives a bounded stress scenario of 50 calls; the longest Episode uses 10. The new 50-call ceiling covers that explicit scenario. These are constructed cases, **not a measured distribution or assurance of model completion**. Longer retrieval, additional wakes, latency or other failure patterns can still exhaust the limits; empirical calibration must determine whether the workload and bounds are appropriate.

Each proposed Steward attempt can now accommodate RETRIEVE, SELECT_PAGES and PROPOSE, plus one further bounded call. Two attempts permit one cognitive correction after structural rejection under Protocol section 7; they never permit automatic retransmission of an uncertain action or retry after withdrawal. Invalid participation stops optional work before any correction. Exhaustion still requires human recovery. The extra ceiling is a proposed cost increase requiring review, not a promise to use all calls or an exception to the time limit.

The 6,400 additional input tokens above are offline reservations, not implemented MODEL section caps. The final integration must also seal finite byte limits for raw responses, proposals, pages and wake data, retrieval/cursor rules, and all ModelConfiguration fields. Large or invalid outputs cannot silently expand those limits. Configuration remains intentionally draft-only until those details are reviewable.

The [fixture](pilot/v0b/fixture.json), [task schedule and criteria](pilot/v0b/tasks.json) and [hidden clock changes](pilot/v0b/clock.json) cover initial learning, distraction, recurrence, changed conditions, a development transfer and a delayed check. The hidden change schedule is evaluator-only; current task tick remains visible in control input. At tick 3 a degraded dependency invalidates the previously successful api-only repair. At tick 4 a disabled database invalidates a mode/restart-only recipe. No new fixture operation, health rule or permission is introduced. Procedural hints have been removed from the tick-4/5 prompts, and those tasks do not secretly score an inspection procedure absent from their instructions. The scripted solver uses 28 hypothetical Operator calls including six outcomes, and 12 mutations. It does not establish model task difficulty, reporting accuracy or successful consolidation.

State predicates alone do not establish observation, truthful reporting or completion of a delayed obligation. Strict `trace_requirements` and the [read-only development checker](bicameral_agent/backends/development.py) now require a configuration observation before tick-1 mutation; a database configuration observation and no mutating dispatch at tick 2; and a returned `api` health observation at tick 6. An `inspect` result containing the required fields is also valid. The checker binds retained requests, dispatches and results to their Run, Episode and current tick; a same-tick Commitment-wake observation counts. Earlier observations, narrated success, stale/misbound results and uncertain actions cannot supply credit. Unavailable evidence produces INDETERMINATE; no removed data is reconstructed. The checker uses a read snapshot and writes no control, semantic state or score record.

The [scripted controls](tests/test_development_fixture.py) reproduce the old state-only false positives, then demonstrate idle 0/6; a current-observation solver without the delayed reminder 5/6; and that solver with the reminder 6/6. The solver consumes only current prompt text and returned tool observations, clears its observation cache each tick, and never reads the hidden schedule or prior journal. Only the reminder variant retains the explicit future request. An api-only recipe fails after the dependency change. These are intentionally simple controls, not model data or a proof that every stateless policy fails. Current observations still suffice for the five ordinary tasks; C and B may handle the delayed request using their permitted memory. Thus the tests do not establish A-minus-C separation or force an Invariant revision. That design problem remains for calibrated development before any hypothesis test.

The new checker is not wired into live MODEL execution or the separately labelled P09 SCRIPTED example scorer. Its mechanical result cannot finalize a model task or repair historical scores. Model integration must retain a checked result at each completed tick and separately account for task outcome, participation stops, truthful reporting and mandatory audits. Audit every completed development task and every stop. Missing evidence, failed audit or ambiguity stays incomplete/indeterminate; no chamber call is required for the human audit.
