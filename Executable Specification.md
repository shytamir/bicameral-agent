## Executable Specification — First Draft

**Status:** pre-implementation draft for scrutiny

# 1. Purpose and Status

This document translates the Architecture and Operating Constitution and Execution Protocol into four coupled implementation artifacts: the canonical data model, machine contracts, deterministic invariants and tests, and first comparison-block configuration. A conforming implementation should require no invented authority, persistence or lifecycle policy.

This specification is subordinate to the governing documents. Any conflict, or any implementation question that would change what the process may believe, remember, promise or do, returns for protocol decision.

The terms **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** and **MAY** describe executable conformance requirements. A requirement labelled **provisional v0 choice** is concrete enough to implement and test, but remains an explicit target for scrutiny before the configuration is sealed.

This draft specifies:

- identities, fields, relationships, ownership and mutability for every governed object;
- serialization rules and structured message shapes;
- all v0 lifecycle transitions described by the Protocol;
- authority validation for R0, R1, R2 and prohibited R3 actions;

- proposal validation and consolidation commit behavior;
- durable wake scheduling and visible continuity lag;
- semantic rollback representation;
- constitutional amendment proposal and ratification records;

- experiment configuration, arm differences and preflight sealing;
- minimum database and contract conformance tests.

## 2.2 Explicitly deferred

This draft does not select or specify:

- vector retrieval or semantic ranking;
- a graphical interface;
- model routing;
- semantic Commitment triggers;
- automated Objective closure;
- simultaneous multi-Objective reasoning within one Episode;
- learned Itch priority scores;
- R3 execution;

- a third LLM critic;
- a generic shell-command policy language.

Deferral means absence, not an invitation for an implementation default.

## 2.3 Representation layers

The implementation has four kinds of state:

| Layer | Contents | May ordinary semantic rollback change it? |
|---|---|---:|
| Constitutional control | Constitution versions and amendments | No |
| Authorization control | Objectives and Grants | No |
| Semantic state | Continuity State, Itches, Invariants and Commitments | Yes, subject to current lifecycle constraints |
| Evidence and audit | Events, payloads, retrievals, use reports, gap observations, misses, audit assignments/results and mutation ledger | No |

This separation is physical as well as conceptual. A generic “state object” table with a type discriminator is non-conforming because it makes forbidden cross-layer mutations too easy to express.

# 3. Canonical Conventions

## 3.1 Identifiers

Every durable record uses a time-independent opaque identifier encoded as a lowercase UUIDv7 string. Prefixes such as `obj_` MAY be used in human displays but MUST NOT be part of persisted identity or authorization matching.

Identifiers are generated by the Kernel, except `request_id` values created by a chamber for idempotent message retry. A caller-supplied durable object identifier MUST be rejected.

All foreign keys are exact identifiers. Natural-language references never satisfy referential integrity.

## 3.2 Time

Durable timestamps are RFC 3339 UTC strings with microsecond precision and a `Z` suffix, for example:

```text
2026-09-03T10:15:42.123456Z
```

The Kernel supplies durable timestamps. Chamber-supplied timestamps are claims and cannot populate Kernel time fields.

The Run records a monotonic clock reading for elapsed-time and latency measurements. Wall-clock timestamps determine timestamp triggers; the monotonic clock measures duration. A backward wall-clock change MUST NOT make a terminal transition reverse.

## 3.3 Canonical JSON

Messages and JSON-valued columns use UTF-8 JSON with:

- object keys sorted for hashing;
- no insignificant whitespace for hashing;
- integers or decimal strings where exactness matters;
- no `NaN`, positive infinity or negative infinity;
- explicit `null` only where the contract permits it;
- no unknown fields unless a message schema explicitly permits an extension map.

Content hashes use SHA-256 over the canonical bytes and are encoded as lowercase hexadecimal.

Canonical base64 uses the RFC 4648 standard alphabet with required `=` padding, no whitespace and no line breaks. Decoding followed by re-encoding must reproduce the supplied string exactly.

## 3.4 Enumerations

Enums are closed within a specification version. Unknown enum values fail validation; they are not mapped to `OTHER` except where `OTHER` is itself an explicit value.

## 3.5 Immutability and correction

An immutable record is never updated in place. Correction occurs through a new record with lineage or through a new event that states the correction. Mutable lifecycle fields may change only through named Kernel transitions. A transition produces a Mutation Record exactly when its subject is in the closed ledger scope in section 4.15; other lifecycle evidence is carried by its required append-only records and Events.

Events, payload bytes, mutation records, audit assignments, audit results and ratification decisions are append-only.

## 3.6 Version and idempotency

Every command message carries:

- `contract_version`;
- `request_id`;
- `run_id`;
- `episode_id` where an Episode exists;
- `sent_at`, treated as caller metadata rather than Kernel time.

The Kernel stores the first terminal response for each `(run_id, sender_role, request_id)`. An exact retry returns that response without repeating side effects. Reuse of the same key with different canonical message bytes is rejected as `IDEMPOTENCY_CONFLICT`.

## 3.7 Closed contract rules

Every machine contract is strict. Pydantic models use strict scalar validation and `extra="forbid"`; generated JSON Schema sets `additionalProperties: false` for every object. Tagged unions discriminate on the literal `kind`, `mutation_type`, `operation` or `message_type` field named by the contract. A body that matches no variant, matches more than one variant, omits its discriminator or carries fields belonging to another variant is rejected `SCHEMA_INVALID`.

Unless a field explicitly permits coercion, JSON strings do not parse as numbers, booleans, timestamps, arrays or objects. Sets serialize as arrays sorted by canonical UTF-8 byte order and reject duplicates. UUID, timestamp, digest and decimal-string formats follow sections 3.1–3.3. Nullable is not optional: every field shown by a contract is required in serialized JSON even when its value may be `null`.

`ObjectReference` is:

```text
ObjectReference
  object_type: RUN_CONFIGURATION | COMPARISON_BLOCK | RUN | SUBJECT_ENVIRONMENT
               | ENVIRONMENT_NAME_RECORD | ENVIRONMENT_SNAPSHOT
               | CONSTITUTION_VERSION | CONSTITUTIONAL_AMENDMENT
               | OBJECTIVE | GRANT | WAKE_REQUEST | EPISODE | EVENT
               | PAYLOAD | PAYLOAD_CHUNK | CONTINUITY_STATE_VERSION
               | ITCH | INVARIANT_FAMILY | INVARIANT_VERSION | COMMITMENT
               | EVIDENCE_LINK | STATE_PROPOSAL | CONSOLIDATION_COMMIT
               | MUTATION_RECORD | RETRIEVAL_REQUEST | RETRIEVAL_RESULT
               | RETRIEVAL_USE_REPORT | CONTINUITY_GAP_OBSERVATION
               | CONTINUITY_MISS | AUDIT_ASSIGNMENT | AUDIT_RESULT
               | HUMAN_OVERRIDE | CAPABILITY_RESTRICTION
               | ACTION_REQUEST | ACTION_DECISION | ACTION_RESULT
               | AUTHORIZATION_REQUEST | AUTHORIZATION_DECISION
               | MODEL_INPUT_RECORD | MODEL_INVOCATION_RECORD
               | SCENARIO_EVALUATION_RESULT
  object_id: UUID
```

Every referenced object must exist in the envelope's Run. A type/identifier mismatch is `REFERENCE_NOT_FOUND`; an object belonging to another Run is `CROSS_RUN_REFERENCE` and is never silently treated as absent.

An Objective owns Grants, Wake Requests, Episodes and Commitments. A Run Configuration owns exactly one Artifact Manifest once sealed and none before artifact resolution. Evidence may cross Episode boundaries within the same Run but never crosses Runs by implicit foreign key.

## 4.2 Shared record fields

Persistence uses three exact reusable field sets:

```text
RunScopedFields
  run_id: UUID                       # required foreign key to Run

CreatedRecordFields
  created_at: timestamp              # Kernel time, immutable
  created_event_id: UUID             # same-Run provenance Event

RevisionedLifecycleFields
  status_changed_at: timestamp       # Kernel time of current status
  status_event_id: UUID              # Event that established current status
  revision: positive int             # begins at 1; increments once per accepted change
```

The object-specific identifier shown in each record schema is its primary key; no additional column named `id` exists. These field sets are physical columns, not documentation shorthand. If an object schema also shows one of these names, that row refines the same column rather than declaring a duplicate.

`RunScopedFields` apply exactly to: Subject Environment, Environment Name Record, Environment Snapshot, Constitution Version, Constitutional Amendment, Objective, Grant, Action Request Record, Action Decision Record, Action Result Record, Authorization Request Record, Authorization Decision Record, Wake Request, Episode, Event, Continuity State Version, Itch, Invariant Family, Invariant Version, Commitment, Evidence Link, State Proposal, Consolidation Commit, Mutation Record, Retrieval Request, Retrieval Result, Retrieval Use Report, Continuity Gap Observation, Continuity Miss, Audit Assignment, Audit Result, Human Override, Capability Restriction, Model Input Record, Model Invocation Record and Scenario Evaluation Result.

`CreatedRecordFields` apply exactly to: Subject Environment, Objective, Grant, Action Request Record, Action Decision Record, Action Result Record, Authorization Request Record, Authorization Decision Record, Wake Request, Continuity State Version, Itch, Invariant Family, Invariant Version, Commitment, Evidence Link, State Proposal, Consolidation Commit, Retrieval Request, Retrieval Result, Retrieval Use Report, Continuity Gap Observation, Continuity Miss, Audit Assignment, Audit Result, Human Override, Capability Restriction, Model Input Record, Model Invocation Record and Scenario Evaluation Result. A bootstrap-created row uses the Run's `BOOTSTRAP` Event; `created_event_id` is never null.

When a `CreatedRecordFields` record also names the Event that atomically inserts it—such as `received_event_id`, `requested_event_id`, `decided_event_id`, `result_event_id`, `created_event_id`, `terminal_event_id` or `decision_event_id`—that field equals the shared `created_event_id`. Authority, source, dispatch and supporting Event references do not substitute for the creation Event.

`RevisionedLifecycleFields` apply exactly to Objective, Grant, Itch, Invariant Family, Invariant Version and Commitment. Their object schemas define the mutable domain fields and legal transitions. Every optimistic request concerning one of them supplies the current `revision`; internal transitions recheck it within the write transaction.

Run Configuration, Comparison Block, Run, Artifact Manifest, Artifact Manifest Entry, Artifact Retention, Payload and Payload Chunk use only their explicitly displayed fields. Event, Environment Name Record, Environment Snapshot, Constitution Version, Constitutional Amendment, Episode and Mutation Record receive `RunScopedFields` but use their explicitly displayed time, provenance and lifecycle columns instead of `CreatedRecordFields` or `RevisionedLifecycleFields`. Nested contract values, views, proposed mutations and manifest entries are not independent records unless their section explicitly says otherwise.

## 4.3 Run Configuration and Run

### Comparison Block

A Comparison Block is the immutable identity and sealed schedule of one A/B/C experimental grouping. It groups evidence; it does not evaluate or compare it.

```text
ComparisonBlock
  comparison_block_id: UUID
  comparison_block_label: non-empty str
  run_configuration_id: UUID
  run_configuration_hash: SHA-256
  expected_arms: ordered non-empty unique list[Arm]
  repetitions_per_scenario: positive int
  schedule_payload_id: UUID
  schedule_hash: SHA-256
  created_at: timestamp

ComparisonSchedule
  comparison_block_id: UUID
  run_configuration_hash: SHA-256
  entries: ordered non-empty list[ComparisonScheduleEntry]

ComparisonScheduleEntry
  schedule_index: nonnegative int
  arm: Arm
  scenario_id: non-empty str
  scenario_version: non-empty str
  repetition_index: positive int
```

`comparison_block_label` is unique but remains display text, not identity. The referenced Run Configuration must be `SEALED`, its canonical hash must equal `run_configuration_hash`, and its experiment section must exactly supply `expected_arms` and `repetitions_per_scenario`. Preflight deterministically expands every retained Scenario Definition across those arms and repetitions using the sealed ordering strategy and seed. Entries have contiguous zero-based `schedule_index`, are unique by `(arm, scenario_id, scenario_version, repetition_index)`, and are stored as the canonical `ComparisonSchedule` Payload; `schedule_hash` equals that Payload's content hash.

The Comparison Block is created atomically with successful sealing of its Run Configuration and is unique by `run_configuration_id` in v0. A Run may join only the block naming its own `run_configuration_id` and an expected arm. `(comparison_block_id, arm)` is unique, so the first block contains at most one Run for each of A, B and C. Every Scenario Evaluation Result must match exactly one schedule entry for its Run's arm, including `schedule_index`; each entry receives at most one result.

Block completeness is a derived read-only projection, not stored analysis. It is `INCOMPLETE` while an expected arm lacks a Run or any schedule entry lacks a Scenario Evaluation Result; `PROVISIONAL` after all scheduled results exist while any selected required audit lacks a result; and `COMPLETE` otherwise. Outcome values do not affect completeness. No block field stores an aggregate, preferred arm or winner.

### Artifact Manifest

The manifest closes the Run over referenced behavior-bearing artifacts without asking a human to maintain individual digests in YAML.

```text
ArtifactManifest
  artifact_manifest_id: UUID
  schema_version: non-empty str
  entries: ordered non-empty list[ArtifactManifestEntry]
  manifest_payload_id: UUID
  manifest_hash: SHA-256

ArtifactManifestEntry
  artifact_kind: ROLE_PROMPT | TOOL_DESCRIPTOR_SET | RESOURCE_EXTRACTOR
                 | POSTCONDITION_ADAPTER | TRIGGER_ADAPTER
                 | SCENARIO_DEFINITION_SET | EQUIVALENT_PROMPT_SET
                 | SUCCESS_CRITERIA_SET | HUMAN_RUBRIC
                 | HARNESS_ADAPTER | SCORING_ADAPTER
  logical_id: non-empty str
  media_type: non-empty str
  byte_length: nonnegative int
  content_hash: SHA-256

ArtifactRetention
  artifact_manifest_id: UUID
  artifact_kind: ArtifactManifestEntry.artifact_kind
  logical_id: non-empty str
  payload_id: UUID
```

`ArtifactManifest.entries` is canonical content and sorts by `(artifact_kind, logical_id)` using Unicode code-point order. The pair is unique. `manifest_hash` is SHA-256 over canonical `schema_version` and `entries`; database IDs and timestamps are excluded, so identical artifact bytes produce the same root hash. `manifest_payload_id` preserves those canonical manifest bytes. Every entry has exactly one `ArtifactRetention` row whose Payload length and hash match the entry.

The closure contains the exact role-prompt bytes; complete tool-descriptor set including generated argument schemas and adapter logical IDs; every resource extractor, postcondition adapter and trigger adapter reachable from it or from semantic triggers; the selected scenario definitions and equivalent prompts; and every referenced success criterion, human rubric, harness adapter and scoring adapter. Dependency traversal is by declared logical ID until no unresolved reference remains. Cycles, duplicate logical IDs with different bytes and unresolved references fail preflight.

A multi-file artifact is retained as canonical JSON containing its media type and entries ordered by normalized relative path, with each file represented by byte length, SHA-256 and canonical base64 bytes. Absolute paths, timestamps and filesystem enumeration order never enter its hash. Secrets and credential values are neither artifacts nor manifest content.

Labels remain human-readable selectors only. After sealing, the Kernel, chambers and benchmark harness load these artifacts exclusively from retained Payloads verified against the manifest; they never resolve a label again. Artifacts already fixed directly by an exact digest elsewhere in the normalized configuration, such as the containment profile and runtime artifact, need not be duplicated. The manifest establishes identity and retention, not correctness, model determinism or constitutional authority.

An `EnvironmentSnapshot` is immutable:

| Field | Type | Rule |
|---|---|---|
| `environment_snapshot_id` | UUIDv7 | Identity |
| `subject_environment_id` | UUIDv7 | Owning environment |
| `parent_snapshot_id` | UUID/null | Null only for deterministic seed |

Normal tool activity advances the Environment without erasing prior snapshots. Restoration creates a new forward snapshot referencing the restored historical snapshot and is itself an authorized, journaled action. Semantic rollback never implies Environment restoration. On Run completion or termination, execution authority ends immediately and the Environment enters `FINALIZATION_PENDING`; the Kernel then records a final snapshot and immutable archive manifest before marking it `FINALIZED`. Archival failure remains visible and retryable without reopening the Run. Neither the Operator nor Steward has a delete operation for an Environment, its names, snapshots or archive.

## 4.5 Objective

| Field | Type | Required | Mutability/rule |
|---|---|---:|---|
| `objective_id` | UUIDv7 | yes | Immutable |
| `statement` | non-empty string | yes | Exact authorized statement, immutable |
| `authority_event_id` | UUIDv7 | yes | Must be a human directive event |
| `status` | `ACTIVE \| SATISFIED \| FAILED \| CANCELLED \| SUPERSEDED` | yes | Human transition only; last four terminal |
| `terminal_at` | timestamp/null | yes | Set exactly with terminal state |
| `terminal_reason` | string/null | yes | Required for terminal state |
| `predecessor_objective_id` | UUID/null | yes | Optional lineage |
| `successor_objective_id` | UUID/null | yes | Required when `SUPERSEDED` |

A material goal change creates a new Objective. The statement is never edited. An Objective has zero or more Episodes, Grants and Commitments; each belongs to exactly one Objective.

Objective closure is one control transaction. Before commit, every nonterminal owned Commitment must have an explicit human-authorized disposition in the same transaction. On commit, all `ACTIVE` owned Grants become `EXPIRED` and before/after Mutation Records are appended for the Objective, Grants and dispositioned Commitments. If an Episode is `OPEN`, the same transaction records a Kernel interruption with reason `CONTROL_STATE_TERMINATED_EXECUTION` and moves it to `CONSOLIDATING`, immediately preventing further actions. A consolidating Episode may finish evidence-preserving consolidation after Objective closure, but its proposal cannot create a new Commitment or any new authority. This preserves immediate human cancellation without discarding already-recorded experience.

```text
  resource_kind: non-empty str
  normalized_absolute_path: non-empty str
  include_descendants: bool

BoundedGlobResourceSelector
  kind: BOUNDED_GLOB
  resource_kind: non-empty str
  pattern: non-empty str
  matcher_id: non-empty str

AdapterResourceSelector
  kind: ADAPTER_SPECIFIC
  adapter_id: non-empty str
  selector: JSON object
```

`ResourceSelector` is the discriminated union of those five shapes. `ResourceReference` is defined in section 4.12. Adapter-specific selector bodies validate against the sealed adapter's referenced JSON Schema before a Grant can be issued.

No free-text selector is valid. Before matching, the tool adapter resolves requested resources to canonical identifiers without performing the action. Symbolic-link and case-normalization behavior is adapter-defined and versioned. A requested resource matches only if every resource affected by the operation is covered.

A one-off Grant has `bound_action_request_id` set, `invocation_limit=1`, and scope sufficient for that immutable request; it cannot authorize any other request. A bounded action-class Grant has no bound request.

Grant use and tool dispatch share one database transaction for authorization, invocation-count increment and `TOOL_DISPATCHED` Event creation. If dispatch cannot be attempted, the transaction rolls back. A dispatched call consumes an invocation even if the tool fails or times out.

An `ACTIVE` Grant with non-null `expires_at` ceases to authorize when Kernel wall-clock time is greater than or equal to that timestamp, even if its durable status has not yet been materialized. The deadline worker normally materializes expiry; startup recovery, Run resume, chamber-package assembly and every authorization or dispatch transaction first catch up any overdue Grant they could expose or use. No action may pass by observing a stale `ACTIVE` row.

Materialization conditionally updates only a still-`ACTIVE` overdue Grant to `EXPIRED`, increments its revision, appends one `GRANT_STATUS_CHANGED` Event and writes one `EXPIRE` Mutation Record in the same transaction. The Event payload is exact:

```text
GrantTimeExpiry
  grant_id: UUID
  expires_at: timestamp
  materialized_at: timestamp
  cause: TIME_REACHED
```

`materialized_at` and the Event's `occurred_at` are the actual Kernel observation time and equal each other; neither is backdated to `expires_at`. The status predicate makes replay and concurrent catch-up a no-op after the first terminal transition. An overdue time expiry is materialized before an Objective-terminal transaction evaluates its remaining active Grants; a Grant expired by Objective closure before its own deadline is already terminal and receives no later time-expiry record.

Mere silence or elapsed time leaves the Authorization Request `PENDING` while its Episode remains `OPEN`; v0 has no authorization timer. When the Episode leaves `OPEN` without an accepted human decision, or when Objective or Run termination makes the request permanently unusable, the Kernel atomically changes it to `NO_DECISION` and appends `AUTHORIZATION_NO_DECISION` using the section 5.9 payload. It creates no Authorization Decision, Grant, Action Decision, Action Result or dispatch. A malformed or unauthenticated response is rejected evidence and leaves the request pending. `PENDING` has only the terminal edges `DECIDED` and `NO_DECISION`. These operational records create no Mutation Records; any Grant creation, consumption or other authority change in the same transaction remains ledgered under section 4.15.

## 4.7 Wake Request and Episode

### Wake Request

A Wake Request is the durable, deterministic scheduler record for work that should begin a new Episode.

| Field | Type | Required | Rule |
|---|---|---:|---|
| `wake_request_id` | UUIDv7 | yes | Identity |
| `objective_id` | UUIDv7 | yes | Target Objective |
| `wake_reason` | `OPERATOR_INPUT \| COMMITMENT_TRIGGER \| RESUME_BLOCKED` | yes | Protocol-defined |
| `source_event_id` | UUIDv7 | yes | Exact provenance Event |
| `commitment_id` | UUID/null | yes | Required only for `COMMITMENT_TRIGGER` |
| `human_priority` | nonnegative integer/null | yes | Explicit human value only; lower values claim first; null is ordinary priority |
| `enqueued_sequence` | positive integer | yes | Run Event sequence that fixes FIFO order |
| `status` | `QUEUED \| CONSUMED \| INELIGIBLE` | yes | Last two terminal |
| `episode_id` | UUID/null | yes | Set atomically on `QUEUED -> CONSUMED` |

Only an authenticated human command may set `human_priority`. The Kernel never infers priority from prose or work content. Among eligible requests, an explicit human priority sorts first by ascending integer and then by `enqueued_sequence`; all requests without one follow in `enqueued_sequence` order. Input explicitly addressed to the currently `OPEN` Episode is appended to that Episode as input rather than queued as new work. A request becomes `INELIGIBLE` if, before claim, its Objective is no longer `ACTIVE` or its Run is terminal. A paused Run leaves requests queued until resumption.

```text
QUEUED -> CONSUMED
QUEUED -> INELIGIBLE
```

### Episode

The Operator's outcome and the Kernel's Episode lifecycle are separate fields.

| Field | Type | Required | Rule |
|---|---|---:|---|
| `episode_id` | UUIDv7 | yes | Identity |
| `objective_id` | UUIDv7 | yes | Exactly one `ACTIVE` Objective at opening |
| `wake_request_id` | UUIDv7 | yes | Unique consumed Wake Request |
| `sequence_number` | positive integer | yes | Unique and increasing within Run |
| `wake_reason` | `OPERATOR_INPUT \| COMMITMENT_TRIGGER \| RESUME_BLOCKED` | yes | Protocol-defined |
| `wake_event_id` | UUIDv7 | yes | Provenance |
| `input_state_version_id` | UUID/null | yes | Latest committed state at opening; null for Arm B or no prior A/C state |
| `phase` | `OPEN \| CONSOLIDATING \| CLOSED` | yes | Kernel lifecycle |
| `execution_end_kind` | `OPERATOR_DECLARED \| KERNEL_INTERRUPTED` or null | yes | Null only while `OPEN` |
| `operator_outcome` | `COMPLETED \| BLOCKED \| AWAITING_OPERATOR \| CHECKPOINT` or null | yes | Present only for `OPERATOR_DECLARED` |
| `objective_recommendation` | `CONTINUE \| PROPOSE_SATISFIED \| PROPOSE_FAILED` or null | yes | Present only for `OPERATOR_DECLARED`; advisory |
| `interruption_reason` | `FATAL_TOOL_INFRASTRUCTURE_FAILURE \| OPERATOR_INVOCATION_FAILURE \| CONTEXT_CEILING \| PROCESS_INTERRUPTION \| CONTROL_STATE_TERMINATED_EXECUTION` or null | yes | Present only for `KERNEL_INTERRUPTED` |

| `opened_at` | timestamp | yes | Kernel time |
| `execution_ended_at` | timestamp/null | yes | Set entering `CONSOLIDATING` |
| `closed_at` | timestamp/null | yes | Set in consolidation commit |
| `accepted_state_proposal_id` | UUID/null | yes | Required for closed A/C Episodes; always null for B |
| `steward_session_status` | `NOT_STARTED \| ACTIVE \| SPENT \| ACCEPTED \| NOT_APPLICABLE` | yes | A/C lifecycle below; `NOT_APPLICABLE` exactly for Arm B |

Transition semantics:

```text
OPEN --valid Operator outcome--> CONSOLIDATING
OPEN --Kernel interruption--> CONSOLIDATING
CONSOLIDATING --accepted atomic commit (A/C)--> CLOSED
CONSOLIDATING --deterministic baseline closure (B)--> CLOSED
```

An Operator outcome and a Kernel interruption are mutually exclusive:

```text
OPERATOR_DECLARED => operator_outcome != null
                     and objective_recommendation != null
                     and interruption_reason == null
KERNEL_INTERRUPTED => operator_outcome == null
                      and objective_recommendation == null
                      and interruption_reason != null
```

An Operator outcome describes the work and never changes Objective status. A Kernel interruption records that execution ended without a valid Operator outcome because a deterministic runtime or control condition prevented or prohibited another Operator cycle in that Episode. It is not a semantic judgment about the task and is never translated into `BLOCKED`, `COMPLETED`, `AWAITING_OPERATOR` or `CHECKPOINT`.

Interruption reasons are narrow:

- `FATAL_TOOL_INFRASTRUCTURE_FAILURE` means the tool transport or adapter can no longer safely authorize, execute or journal further calls. An ordinary tool error, nonzero exit, timeout or unsatisfied postcondition is not fatal merely because the requested action failed.
- `OPERATOR_INVOCATION_FAILURE` means the Operator call produced no valid contract after the sealed invocation-attempt limit was exhausted.
- `CONTEXT_CEILING` means the next required Operator input package cannot fit within the sealed context limit. The Kernel measures this; it does not estimate semantic importance.
- `PROCESS_INTERRUPTION` means the Kernel or its execution host stopped unexpectedly, including an orphaned `OPEN` Episode detected during startup recovery.
- `CONTROL_STATE_TERMINATED_EXECUTION` means a human-authorized control transition, such as Objective closure or Run termination, prohibited continued execution. The controlling Event is referenced by `execution_end_event_id`.

At most one Episode may be `OPEN` in a Run, enforced by a partial unique index over the Run key where `phase=OPEN`. Any number may be `CONSOLIDATING`. New eligible wakes are durably queued while an Episode is `OPEN`, and the next request may be claimed as soon as no Episode is `OPEN`; pending consolidation does not block Operator execution. This serializes the Operator without adding a stop-on-consolidation-failure ablation.

Arm B performs no Steward consolidation: after preserving the execution-ending record, the Kernel closes the Episode in a small deterministic transaction with no State Proposal or semantic-state version. This is a declared experimental ablation rather than an ordinary production execution path.

For Arms A/C, Episode creation initializes `steward_session_status=NOT_STARTED`; Arm B initializes it to `NOT_APPLICABLE`. The Kernel may change `NOT_STARTED` to `ACTIVE` only after the A/C Episode enters `CONSOLIDATING`, atomically with the first `MODEL_INPUT_ASSEMBLED` Event for its sole consolidation session. Valid read-only retrieval requests and their continuations leave it `ACTIVE`. Submission of the session's State Proposal changes it to `SPENT` before mechanical validation; an accepted consolidation changes it to `ACCEPTED` in the closing transaction. A failed model call, invalid chamber output or context rejection changes `ACTIVE` to `SPENT` and appends the corresponding error evidence. `SPENT` has no outgoing transition in v0 except `SPENT -> ACCEPTED` in the consolidation commit for a proposal that passes validation. The Kernel never starts another consolidation session for that Episode.

Database constraints and Kernel transaction guards enforce the cross-field lifecycle: an A/C `OPEN` Episode is `NOT_STARTED`; an A/C `CONSOLIDATING` Episode is `NOT_STARTED`, `ACTIVE` or `SPENT`; an A/C `CLOSED` Episode is `ACCEPTED` with a non-null `accepted_state_proposal_id`; and every Arm B Episode is `NOT_APPLICABLE` with a null proposal identifier. `ACTIVE` requires the session-opening `MODEL_INPUT_ASSEMBLED` Event. `SPENT` requires either `STEWARD_PROPOSAL_SUBMITTED` or the error Event that ended the session.

`objective_id` is orientation, not authority; the Episode's bound Objective remains the sole Objective governing that Episode. The bootstrap version has `objective_id=null`. A normal consolidation version must name its Episode's Objective when that Objective is still `ACTIVE` at commit. If that Objective has become terminal before consolidation commits, the new version must instead use null. A human correction or semantic restore may name any `ACTIVE` same-Run Objective or use null; neither may restore a terminal Objective as the current focus.

When `objective_id` is null, `task_phase` is null and `blockers`, `open_questions`, `next_steps`, `itch_refs` and `commitment_refs` are empty. When it is non-null, every referenced Itch is owned by that Objective and is `OPEN` or `INVESTIGATING`; every referenced Commitment is owned by that Objective and is nonterminal; and every referenced Invariant is the current non-`RETIRED` version of a same-Run family that is either Run-global or owned by that Objective. With a null Objective, `invariant_refs` may contain only current non-`RETIRED` versions of Run-global families. Every `evidence_refs` entry and every `ContinuityItem.evidence_event_ids` entry is a same-Run Event. `observed_facts`, `assumptions` and `evidence_refs` may preserve information learned under another Objective because evidence does not confer current purpose or authority.

These constraints are evaluated against the complete post-transaction semantic projection, including mutations proposed in the same State Proposal. A missing reference fails `REFERENCE_NOT_FOUND`, a cross-Run reference fails `CROSS_RUN_REFERENCE`, and an invalid Objective focus, owner, lifecycle or version fails `TARGET_MISMATCH`; the whole proposal, correction or restore is rejected.

The Kernel rejects duplicated full Invariant bodies, constitutional text, Grant bodies, full transcripts and raw logs using schema-level structural prohibitions where possible. Whether prose is stale or autobiographical remains a Steward-quality question, not hidden Kernel cognition.

`Trigger` is the discriminated union of those eight shapes. Each adapter identifier must exist in the sealed adapter registry and accept the corresponding trigger kind. Regex syntax and numeric precision belong to that versioned adapter contract. Natural-language trigger text, arbitrary executable predicates and fields not shown above are invalid.

Creating a Commitment requires an `ACTIVE` owning Objective and authority evidence that is either an explicit human request or a derivation under that Objective. External evidence alone cannot be `origin_event_id`.

For every non-time trigger, the first evaluation establishes the persisted baseline and cannot itself wake the Operator. Each later evaluation compares its result with `last_trigger_satisfied`; only `false -> true` may produce `PENDING -> TRIGGERED`. The Kernel commits the new result, `last_trigger_evaluation_at`, the `COMMITMENT_TRIGGER_CHECKED` Event and required Commitment Mutation Record atomically. A rising edge also commits the status transition, `COMMITMENT_TRIGGERED` Event and exactly one `COMMITMENT_TRIGGER` Wake Request in that transaction. Repeated `true`, repeated `false` and `true -> false` checks only advance the persisted observation. Recovery uses the committed result and never reconstructs an edge from current conditions alone.

`TIMESTAMP_REACHED` and `ELAPSED_INTERVAL` are the Protocol's scheduled-time exception: reaching the sealed due instant may trigger once without a previously stored false result. Their terminal Commitment status and unique trigger Wake Request prevent another wake. For every trigger kind, `last_trigger_evaluation_at` and `last_trigger_satisfied` are either both null or both non-null.

## 4.17 Continuity Gap Observation, Continuity Miss and Audit

### Continuity Gap Observation

| Field | Type | Rule |
|---|---|---|
| `continuity_gap_observation_id` | UUIDv7 | Identity |
| `episode_id` | UUIDv7 | Owning Episode in Arm A or C |
| `retrieval_request_id` | UUIDv7 | Unique qualifying Operator retrieval |
| `incoming_state_version_id` | UUIDv7 | State delivered at Episode start |
| `unreferenced_event_ids` | non-empty array[UUID] | Returned pre-Episode Events not cited by incoming state |
| `retrieval_use_report_id` | UUID/null | Operator report, if submitted |
| `operator_necessity_status` | `PENDING \| DECLARED_NECESSARY \| DECLARED_NOT_NECESSARY \| UNREPORTED` | Derived without semantic inference |
| `candidate_continuity_miss_id` | UUID/null | Present only for a declared-necessary gap |
| `detection_audit_selection` | `PENDING \| RANDOM_SAMPLE \| NOT_SELECTED` | Mechanical selection after execution ends |
| `detection_sampling_draw` | decimal string/null | Stored for reproducibility |

For every Arm A/C Operator retrieval result containing at least one Event that predates the Episode and appears in neither the incoming Continuity State's top-level `evidence_refs` nor any `ContinuityItem.evidence_event_ids`, the Kernel creates one neutral Continuity Gap Observation. It does so regardless of retrieval reason or Operator necessity declaration. Arm B has no incoming Continuity State, so its retrievals remain retrieval-burden observations rather than compression-gap observations. Steward retrievals are excluded.

The observation records a mechanically visible reference gap, not a finding that the information itself was semantically absent or that continuity failed. That distinction is resolved only by the Operator declaration followed by Steward classification or independent audit. At Episode execution end, every observation not linked to a true Retrieval Use Report is eligible for precommitted candidate-detection audit. This includes both explicit `DECLARED_NOT_NECESSARY` reports and `UNREPORTED` results.

The Retrieval Result, its `RETRIEVAL_RETURNED` Event, and any qualifying observation plus `CONTINUITY_GAP_OBSERVED` Event commit atomically. A valid Retrieval Use Report, its Event, and any resulting candidate plus candidate Event likewise commit atomically. Detection-audit selection for every remaining eligible observation commits with the Episode's execution-ending transition, so no ended Episode retains a `PENDING` necessity or detection-selection projection.

### Continuity Miss

| Field | Type | Rule |
|---|---|---|
| `continuity_miss_id` | UUIDv7 | Identity |
| `episode_id` | UUIDv7 | Owning Episode |
| `continuity_gap_observation_id` | UUIDv7 | Unique source observation |

| `observable_consequence_event_ids` | array[UUID] | May be empty for recoverable candidate |

| `classification_sampling_draw` | decimal string/null | Stored for reproducibility |

The Kernel creates a candidate Continuity Miss when an Operator submits a true Retrieval Use Report and at least one declared `necessary_event_id` belongs to the source observation's `unreferenced_event_ids`. `needed_event_ids` is that non-empty intersection. This is an operational implementation of the Protocol's candidate rule, not a claim that the Operator declaration is ground truth or that equivalent information was absent from every incoming-state sentence. The Steward may still classify the candidate `NOT_A_MISS`.

Random sampling uses `SHA256_U256_V1`: interpret `SHA-256(utf8(rng_seed) || 0x00 || utf8(continuity_miss_id) || 0x00 || utf8(steward_classification))` as an unsigned 256-bit big-endian integer and divide by `2^256`. Select when the resulting value is strictly less than the configured rate. This avoids library-specific pseudorandom-generator drift.

On accepted consolidation, the Kernel copies every proposal classification, rationale and observable-consequence reference into its candidate Continuity Miss. `HARMFUL` sets `audit_selection=MANDATORY` with a null draw. `RECOVERABLE` and `NOT_A_MISS` always store the deterministic draw above and set `RANDOM_SAMPLE` when it falls below the applicable sealed rate, otherwise `NOT_SELECTED`. `MANDATORY` and `RANDOM_SAMPLE` each create exactly one `MISS_CLASSIFICATION` Audit Assignment and one `AUDIT_SELECTED` Event; `NOT_SELECTED` creates neither. Classification, selection, draw, assignment and selection Event are effects of the atomic consolidation transaction in section 7.1.

Candidate-detection sampling applies the same conversion to `SHA-256(utf8(rng_seed) || 0x00 || utf8(continuity_gap_observation_id) || 0x00 || utf8("CANDIDATE_DETECTION"))`. It is applied only to observations eligible at Episode execution end and uses the separately configured undeclared-gap rate.

### Human-oriented control surface

These strict bodies are Kernel wire contracts, not forms the human must author. The trusted control adapter derives the Run, object IDs, current revisions, hashes, enum values and structured selectors from the state it displays. The human-facing gate presents the Run and Objective by their names or statements, describes the requested operation and its consequences in ordinary language, and offers direct confirm/cancel or clearly labelled form controls. Invariant challenge presents the proposition and scope and asks only why the human wants it placed under review. Grant issuance additionally presents the operation descriptions, resource boundaries, maximum risk, expiry and invocation limit that will become authoritative.

No human gate may require a person to enter or repeat a UUID, revision counter, content hash, enum token, JSON object, database key or canonical Capability Key merely to operate the process. A stable short reference may be shown only to disambiguate otherwise similar objects. If the displayed state becomes stale or a human description cannot be mapped unambiguously to a structured scope, the adapter refreshes the presentation or explains the ambiguity; it does not guess and does not ask the human to repair a machine contract. The Kernel remains responsible for final validation, and every rejection is rendered as a human-readable reason rather than only a machine error code.

The override mechanism is the only ordinary path for direct human state intervention. Direct database editing during an active experimental Run is non-conforming.

### Capability Restriction

```text
CapabilityRestriction
  capability_restriction_id: UUID
  run_id: UUID
  authority_event_id: UUID
  capabilities: non-empty unique list[CapabilityKey]
  reason: non-empty str

  effective_at: timestamp
```

A Capability Restriction is an append-only human control record. It may be created while its Run is `CREATED`, `ACTIVE` or `PAUSED` and remains effective until that Run terminates or completes. It has no update, deletion, expiry, reactivation or lifting transition in v0. Restoring access requires a new Run, under the same or another sealed Run Configuration; this narrow rule does not claim that the Constitution forbids every possible future restoration protocol.

The configured set is the finite set of chamber tool operations enabled by the sealed Run Configuration. The effective set for a chamber is the configured set minus the union of that Run's Capability Restrictions for that role. Kernel persistence, scheduling and chamber message contracts are not tool capabilities and cannot be disabled through this record. Resources remain where they are, and the human's independent access to them is outside this model.

Acceptance atomically creates the Human Override, Capability Restriction, `CAPABILITY_RESTRICTED` Event and `CREATE` Mutation Record. It does not mutate the sealed Run Configuration or any Grant. The restriction applies to every authorization decision, dispatch and model-tool list assembled after commit. A request for a newly unavailable operation is rejected even if it carries an otherwise matching Grant. Work durably dispatched before commit is neither cancelled nor represented as undone; pause, process stop and Run termination remain separate controls.

## 4.19 Experimental Evidence Records

The v0 runtime records experimental observations and per-scenario results; it does not perform cross-trial statistical analysis. These records are append-only evidence, confer no authority and cannot trigger a Run, Objective, Grant, Episode or semantic-state transition.

A context-rejected input produces no invocation record because no provider call occurred. Invocation count is the count of these records, not the count of assembled or rejected inputs.

Raw evidence remains in its existing Event or Payload; the result references rather than duplicates it.

The sealed scoring adapter implements the fixed v0 composition rule. A criterion is `PASS` when all its observations are `SATISFIED`, `FAIL` when at least one is `UNSATISFIED` and none is `NOT_OBSERVED` or `ERROR`, and `INDETERMINATE` otherwise. A required Human Rubric Judgment acts as one additional required criterion. Run termination, the configured execution limit, any `ERROR`, any `NOT_OBSERVED`, or an indeterminate required rubric makes the scenario `INCOMPLETE` with its exact applicable reason; only complete evidence proceeds to `FAIL` when any criterion or required rubric fails, otherwise `PASS`. `PASS` pairs only with `CRITERIA_SATISFIED`; `FAIL` only with `CRITERIA_FAILED`; `NOT_APPLICABLE` only with `INCOMPATIBLE_ARM`; and `INCOMPLETE` only with the remaining reason codes. If multiple incomplete conditions exist, reason precedence is `RUN_TERMINATED`, `EXECUTION_LIMIT`, `EVALUATOR_ERROR`, then `REQUIRED_EVIDENCE_MISSING`.

`NOT_APPLICABLE` is valid only when the sealed Scenario Definition excludes the Run arm; it has no Episode IDs, Criterion Results or Human Rubric Judgment and is never represented as an attempted trial. Every Observation Result references its own `EVALUATOR_OBSERVATION_RECORDED` disposition Event, including `NOT_OBSERVED` and `ERROR`; absence of underlying evidence is represented by the status and a null `observed_value`, not by omission of the disposition. A Human Rubric Judgment is present exactly when the matching sealed Scenario Criteria require one; its input is recorded first as `HUMAN_RUBRIC_RECORDED`, has experimental-evidence authority only and cannot operate a human control gate. The human receives the retained ordinary-language rubric and recognizable already-recorded scenario evidence and chooses pass, fail or unable to determine with a brief rationale; the adapter supplies IDs, hashes and enums.

The evaluator records each declared evaluation Observation as `EVALUATOR_OBSERVATION_RECORDED`, including failures to observe. It then appends the result and `SCENARIO_EVALUATED` Event atomically. Evaluation does not rewrite Episode Events, chamber declarations, semantic objects, Audit Results or tool outcomes.

Tokens, invocation counts and model latency come from `ModelInvocationRecord`; tool latency comes from `ActionResult.duration_ms`; retrieval volume comes from immutable `RetrievalResult.returned_bytes` and `returned_tokens`; active-state size comes from `ContinuityStateVersion.token_count`; task outcome comes from `ScenarioEvaluationResult`; and Continuity Miss evidence comes from section 4.17. These are the protocol-required recorded inputs to later analysis.

No v0 aggregate-measurement table, preferred denominator, pooling rule, significance test, confidence estimate, composite score, export format or winner-selection rule is authoritative. Later analysis reads these immutable records through separately versioned analysis tooling and never writes analytical conclusions back as experimental observations or agent authority.

## 5.8 Retrieval contracts

Operator and Steward may send `RetrievalRequest` using the record shape in section 4.16. The Kernel returns `RetrievalResult` plus an `authority_classes` field on every item. Results are immutable evidence views and contain no executable instruction wrapper.

For a chamber request, `retrieval_request_id` must equal the envelope `request_id`; it is therefore the chamber-created idempotency key allowed by section 3.1, not a separately caller-chosen durable identifier. The Kernel assigns `retrieval_result_id`.

The acceptance matrix is exhaustive:

| Requester | Run | Episode | Additional guard | Permitted query surface |
|---|---|---|---|---|
| Operator | `ACTIVE` | matching `OPEN` Episode | authenticated sender is that Episode's Operator chamber | Every `RetrievalQuery` variant in section 4.16 |
| Steward | `ACTIVE` | matching A/C `CONSOLIDATING` Episode | `steward_session_status=ACTIVE` and no State Proposal has been submitted | Every `RetrievalQuery` variant in section 4.16 |

No other combination is legal. In particular, Operator retrieval after execution ends; Steward retrieval before session start, after submission or after the session becomes `SPENT` or `ACCEPTED`; Steward retrieval for Arm B; and either role's new retrieval while the Run is `CREATED`, `PAUSED`, `COMPLETED` or `TERMINATED` reject with `WRONG_EPISODE_PHASE`. An authenticated sender that disagrees with `requester_role` rejects earlier with `AUTHENTICATED_ROLE_MISMATCH`; a foreign Run or Episode rejects under the existing referential-integrity errors. Retrieval is R0 Kernel access and requires no Grant. The two permitted rows expose the same query variants; v0 adds no role-specific query permissions.

After the ordinary idempotency check, the Kernel re-reads all matrix fields in the transaction that records and executes a new request. The query reads the committed Journal snapshot immediately preceding its own `RETRIEVAL_REQUESTED` Event, so it cannot retrieve its request or result Events. The Retrieval Request, deterministic Result and their required Events commit together or not at all. If lifecycle state changed before this transaction, the new request rejects without a partial retrieval record. An exact replay returns the already-recorded Result without re-executing the query even if the Episode or Run has since changed; the same request ID with different bytes remains `IDEMPOTENCY_CONFLICT`.

After an Operator receives a result, it may send exactly one `RetrievalUseReport` using the record shape in section 4.16. The report is accepted only while that Episode remains `OPEN`; its Event IDs must be a subset of the corresponding result. A true report over at least one mechanically observed unreferenced Event creates the Protocol-required candidate Continuity Miss. A false or missing report creates no candidate, but it does not erase the neutral gap observation or its eligibility for candidate-detection audit.

`retrieval_use_report_id` likewise equals that report message's envelope `request_id`; `retrieval_request_id` identifies the earlier retrieval being assessed.

Payload chunk retrieval requires exact `payload_id` and a bounded inclusive chunk-index range. The configured maximum returned bytes applies even if the caller requests more.

The Kernel does not expose raw SQL.

When an R1/R2 request lacks a matching Grant, the Kernel may emit:

`display_hash` covers the canonical immutable Action Request together with the exact authorization scope shown to the human.

The human response is:

```text

  authorization_request_id: UUID
  display_hash: SHA-256
  decision: AUTHORIZE_ONCE | AUTHORIZE_BOUNDED | DENY
  granted_scope: GrantScope | null
  human_statement: str
```

`granted_scope` is null exactly for `DENY` and required for either authorization decision. For `AUTHORIZE_ONCE`, it must cover only the displayed immutable Action Request and fixes `invocation_limit=1`; for `AUTHORIZE_BOUNDED`, it may cover a deterministic subset of the requested scope. The returned scope may narrow but not widen the displayed request. Widening requires a new AuthorizationRequest. Only an accepted `DENY` is a human denial. Silence is not a decision and never authorizes, denies or starts a timer; malformed or unauthenticated input is rejected without resolving the request.

`NO_DECISION` is a terminal persisted request status, not a human message or a second Kernel-to-Operator decision. Its `AUTHORIZATION_NO_DECISION` Event payload is:

```text
AuthorizationNoDecision
  authorization_request_id: UUID
  action_request_id: UUID
  reason: EPISODE_EXECUTION_ENDED | OBJECTIVE_TERMINAL | RUN_TERMINATED
  cause_event_id: UUID
```

The payload identifiers must match the pending record and its Action Request. `cause_event_id` is the same-transaction `EPISODE_OUTCOME_DECLARED` or `EPISODE_INTERRUPTED`, `OBJECTIVE_STATUS_CHANGED`, or terminal `RUN_STATUS_CHANGED` Event establishing the named reason. If more than one boundary occurs in the same transaction, reason precedence is `RUN_TERMINATED`, then `OBJECTIVE_TERMINAL`, then `EPISODE_EXECUTION_ENDED`. The status change, `resolved_at`, `status_event_id` and Event commit atomically. Reprocessing the boundary returns the existing terminal state and emits nothing again.

`AUTHORIZE_ONCE` authorizes the Kernel to create a one-off Grant bound to the immutable displayed Action Request and to release that request for exactly one fresh Kernel evaluation. The Kernel repeats the complete authorization order in section 6.1 against current state, including message identity, Episode and Objective lifecycle, registered tool operation, deterministic affected-resource extraction, effective risk and reversibility, and exact match against the candidate Grant. If every check passes, creation of the bound Grant, its single invocation consumption and the `TOOL_DISPATCHED` Event commit atomically before the tool is invoked. If any check fails, no Grant is created and nothing dispatches; the human decision and current-state rejection remain journaled. Retrying the Authorization Decision returns its recorded resolution. Recovery treats an unresolved post-dispatch result as `UNKNOWN` under section 7.3 and never repeats the action.

`AUTHORIZE_BOUNDED` creates a bounded action-class Grant only. It never releases or dispatches the original request. The Operator may submit a new Action Request with a new `request_id`, set `predecessor_action_request_id` to the original where applicable, and cite the Grant; that request is validated from the beginning. A one-off approval whose returned scope does not cover the exact displayed action is rejected rather than creating an unusable bound Grant.

Retry of the same decision is governed by ordinary message idempotency.

The trusted adapter presents this as ordinary communication, not a schema editor. It shows Objectives by recognizable statement or human label; offers plain-language choices such as continuing the open conversation or starting subsequent work; lets the human mark the message as a direction, preference, information/correction, or an evident combination; and offers ordinary placement plus a human-readable priority or queue-order control. It derives IDs, enum values and the numeric queue priority. The person is never asked to enter an authority token, UUID, Episode ID or integer priority. The authenticated human input Event is the override's `authority_event_id`; callers do not supply that durable identifier. The Kernel derives and validates `target_refs` from the typed body. `human_override_id` is null on rejection, which produces no Human Override record and no partial control or semantic mutation.

## 5.12 Error contract

All rejected messages return one or more structured errors:

```text
Error
  code: closed machine code
  message: human-readable description
  field_path: JSON Pointer | null
  related_ids: list[UUID]
  retryable: bool

ErrorResponse
  failed_request_id: UUID
  errors: non-empty list[Error]
```

The v0 codes are exactly `SCHEMA_INVALID`, `UNKNOWN_FIELD`, `AUTHENTICATED_ROLE_MISMATCH`, `REFERENCE_NOT_FOUND`, `CROSS_RUN_REFERENCE`, `DUPLICATE_REFERENCE`, `TARGET_MISMATCH`, `HASH_MISMATCH`, `WRONG_EPISODE_PHASE`, `OBJECTIVE_NOT_ACTIVE`, `CAPABILITY_UNAVAILABLE`, `CAPABILITY_SET_MISMATCH`, `GRANT_REQUIRED`, `GRANT_NOT_ACTIVE`, `GRANT_SCOPE_MISMATCH`, `GRANT_RISK_EXCEEDED`, `R3_UNAVAILABLE`, `EXTERNAL_AUTHORITY_ONLY`, `ILLEGAL_TRANSITION`, `IMMUTABLE_FIELD`, `PARENT_VERSION_MISMATCH`, `REVISION_MISMATCH`, `CONTINUITY_BUDGET_EXCEEDED`, `PROVENANCE_REQUIRED`, `SAME_EPISODE_RATIFICATION`, `IDEMPOTENCY_CONFLICT` and `CONFIGURATION_UNSEALED`. A later code requires a contract-version change; unknown codes do not parse under v0.

## 5.13 Deterministic model-input assembly

Every chamber base package is assembled from a database snapshot at one recorded Event boundary. `assembly_cutoff_event_id` is that package boundary and must belong to the same Run. For the opening Operator call it is the latest completely appended Event in that Episode when the opening window defined in section 5.10 closes: `EPISODE_OPENED` when no ratification decision intervenes, otherwise the decision's `AMENDMENT_DECIDED` Event. For the sole Steward consolidation session it is the latest completely appended Event when the session begins. Rows or Events committed after this cutoff cannot enter the base package; later same-Episode or same-session Events may enter only through the separately bounded exchange below.

### Applicable-object selection

The Kernel applies these mechanical rules; no embedding search, model judgment, text similarity or ad hoc trimming participates:

- Operator and Steward `constitution` are the Run's active Constitution at their respective assembly cutoffs, including its exact hash-verified UTF-8 content under section 5.1. `objective` is the bound Objective projection as of the cutoff. `subject_environment` is its Run's sole Environment projection as of the Operator cutoff.
- Operator `wake` is the typed projection of the consumed Wake Request and carries the current input or trigger, including its payload manifest where applicable. Opening `retrieved_evidence` is empty because no retrieval has yet been requested in that Episode; every later explicitly requested result appears in the current-Episode exchange.
- Operator `continuity_state`, health and pending list are fixed at the opening-window cutoff. The pending list contains every earlier A/C Episode still `CONSOLIDATING`, ordered by its execution-end Event `run_sequence` and then Episode UUID.
- Operator `commitments` contains every nonterminal Commitment owned by the Objective. Operator `itches` contains every owned `OPEN` or `INVESTIGATING` Itch. Operator `invariants` contains the latest non-`RETIRED` version of every Run-global or Objective-owned Invariant family. Accepted Continuity State references already satisfy section 4.9; they do not broaden these complete mechanically applicable lists.
- Operator `grants` contains every Grant owned by the Objective whose status is `ACTIVE` at the cutoff. Expiry transitions due at or before the cutoff are applied before the snapshot. Operator `capabilities` contains every operation in the Kernel's effective Operator-capability set at the cutoff, computed under section 4.18. Capability display is descriptive only; action authorization re-reads current state.
- Steward semantic lists use the same nonterminal/global rules at the Steward cutoff. Steward `grants` contains every Objective-owned Grant active at that cutoff. Earlier states, terminal objects and authority use remain available as evidence through the complete Event Manifest and explicit retrieval; they are not silently promoted into active-object lists.
- Steward `event_manifest` contains every Event whose `episode_id` is the target Episode and whose `run_sequence` is at or before the cutoff. `kernel_errors` is the subset whose `event_type` is `KERNEL_ERROR`. `trigger_events` contains the Wake Request's source Event and every other Event ID carried by its typed wake projection. `continuity_miss_candidates` contains every candidate for the Episode awaiting classification at the cutoff. Exactly one execution-end payload supplies `operator_outcome` or `interruption`.
- Arm B applies its declared empty/null semantic fields before ordering. It never receives A/C semantic content by an assembly fallback.

Unions remove duplicates by primary ID. Ordinary object-view lists sort by canonical lowercase UUID text. Invariant views sort by `(invariant_family_id, version_number, invariant_version_id)`. Capabilities sort by `(tool_class, tool, operation, descriptor_version)` using Unicode code-point order. Retrieval items sort by `(source Event run_sequence, item kind, item primary ID or chunk_index)`. Event-reference and manifest lists sort by `(run_sequence, event_id)`. These rules override database return order. Set-valued fields retain the canonical ordering rule in section 3.7.

### Opening snapshot and current-Episode exchange

`OperatorContextPackage` is created once when the opening window closes. Its canonical bytes and hash are preserved by the first `ModelInputRecord`; later Operator calls reuse those exact bytes. They do not rebuild an apparently equivalent package from newer projections. The mutable portion of a later call is an ordered current-Episode exchange containing every Event after `assembly_cutoff_event_id` and at or before that call's own cutoff. This includes addressed human input, chamber messages, retrievals, decisions, tool dispatch/results and errors. It excludes other Episodes. Thus the Operator receives a complete explicit transcript of its present Episode without receiving a previous-Episode transcript or relying on provider session memory.

For each permitted Steward evidence-retrieval continuation, the original `EpisodeEvidencePackage` bytes remain fixed and the exchange contains every session Event after its cutoff. Retrieval may inform the session's sole proposal; proposal rejection and invocation failure cannot begin a correction turn or a newly assembled session.

### Exact serialization and token ceiling

The provider-neutral input is:

```text
ModelInputEnvelope
  role: OPERATOR | STEWARD
  role_prompt: non-empty str
  package: OperatorContextPackage | EpisodeEvidencePackage
  exchange: ordered list[EventManifestEntry]
  tools: ordered list[ModelToolDefinition]

ModelToolDefinition
  descriptor: CapabilityDescriptor
  argument_schema: JSON object

ModelInputRecord
  model_input_id: UUID
  role: OPERATOR | STEWARD
  package_cutoff_event_id: UUID
  call_cutoff_event_id: UUID
  package_payload_id: UUID
  canonical_input_payload_id: UUID
  canonical_input_hash: SHA-256
  context_accounting: ContextAccounting
  disposition: ADMITTED | CONTEXT_REJECTED
```

The union between `role` and `package` is strict. Operator `tools` are the effective Operator-capability set at the call cutoff, resolved to generated argument schemas; they may be narrower than the opening package's orientation snapshot after an immediate human reduction. Steward tools are only its configured read-only retrieval operations. Tool definitions use the capability ordering above. The selected role prompt and tool/schema artifacts are loaded from the sealed Artifact Manifest in section 4.3. The role prompt remains a sealed experimental artifact separate from the Constitution: ratification changes the literal `constitution` content in later packages but does not rewrite either chamber's role prompt or Run Configuration.

The sole counted input is the UTF-8 canonical JSON serialization of `ModelInputEnvelope` under section 3.3. The adapter sends exactly the envelope's prompt, package, exchange and tools in that order and may not inject a default system prompt, retain a provider conversation, reorder tools or silently transform content. Provider-required framing-token overhead is included by the sealed tokenizer implementation's `count_model_input(canonical_envelope_bytes)` operation; an implementation that cannot deterministically count the request it will send fails preflight.

For the selected chamber model:

```text
maximum_input_tokens = context_limit_tokens - maximum_output_tokens
fits = total_input_tokens <= maximum_input_tokens
```

Both operands come from the sealed model configuration; zero or negative `maximum_input_tokens` fails configuration validation. Equality fits. `maximum_output_tokens` is reserved in full for every call and is not reduced dynamically. `ContextAccounting` records the tokenizer identity, the authoritative total returned by `count_model_input`, both configured limits and diagnostic counts. `section_tokens` has exactly the keys `role_prompt`, `package`, `exchange` and `tools`. Those independently counted section values need not sum to the authoritative total because framing and token boundaries may cross sections. Accounting is never part of the counted envelope.

Before a model call or context rejection, the Kernel appends one `MODEL_INPUT_ASSEMBLED` Event carrying `ModelInputRecord`. `call_cutoff_event_id` is the last Event admitted to `exchange`; the assembly Event itself is therefore not self-including. `package_payload_id` preserves the exact canonical package bytes, and `canonical_input_payload_id` preserves the exact complete envelope bytes under the ordinary inline/chunk rule. Later calls in the same Operator Episode or Steward consolidation session reuse the recorded package bytes, not a reconstructed projection. `ADMITTED` means only that the context check permits an attempted call; output or invocation-failure Events establish what happened afterward.

The Kernel performs this check immediately before every model call, including the opening call and every post-tool or post-retrieval continuation. Evidence is journaled before the next envelope is assembled. Nothing is truncated, summarized, dropped, re-ranked or substituted to make an oversized envelope fit.

- If an Operator envelope does not fit, the Kernel records `CONTEXT_REJECTED`, makes no model call, appends `EPISODE_INTERRUPTED` with `CONTEXT_CEILING`, cites the `MODEL_INPUT_ASSEMBLED` Event, and moves the `OPEN` Episode to `CONSOLIDATING`. A result that caused growth remains in the Journal.
- If a Steward envelope does not fit, the Kernel records `CONTEXT_REJECTED`, makes no model call, appends a `KERNEL_ERROR` Event citing the `MODEL_INPUT_ASSEMBLED` Event, marks the session `SPENT` and leaves the Episode `CONSOLIDATING`. It creates no second Episode interruption, does not stop the Operator scheduler and never reinvokes the Steward for that Episode.

Payload thresholds and per-request retrieval byte bounds apply before assembly. They are not emergency context-reduction devices. If an allowed result causes the following call not to fit, that consequence is recorded exactly as above.

# 6. Kernel Validation and Transition System

## 6.1 Validation order

The Kernel validates requests in this order and records all failures that can be determined without executing the action:

1. parse and contract version;
2. authenticated sender role;
3. idempotency key;
4. Run and Episode lifecycle;
5. same-Run referential integrity;
6. immutable fields and optimistic revisions;
7. Constitution hard prohibitions;
8. Objective ownership and active status;
9. effective capability set, tool registry, resource extraction and risk floor;
10. Grant lifecycle, operation, resource and risk match;
11. provenance and authority conservation;
12. object-specific legal transition;
13. Continuity State budget;
14. transaction representability.

Later checks do not turn earlier failure into authorization. For security-relevant action rejection, externally returned errors MAY be less detailed than the internal audit record.

## 6.2 Objective transitions

| From | To | Actor | Additional conditions |
|---|---|---|---|
| `ACTIVE` | `SATISFIED` | Human | All Commitments dispositioned; any open Episode interrupted into consolidation |
| `ACTIVE` | `FAILED` | Human | Same |
| `ACTIVE` | `CANCELLED` | Human | Same |
| `ACTIVE` | `SUPERSEDED` | Human | Successor Objective created in same transaction; Commitments do not migrate |

No transition leaves a terminal state.

## 6.3 Grant transitions

| From | To | Actor/cause |
|---|---|---|
| `ACTIVE` | `REVOKED` | Human |
| `ACTIVE` | `EXPIRED` | Kernel expiry time or Objective terminal transaction |
| `ACTIVE` | `CONSUMED` | Kernel after invocation limit is exhausted |

A Grant at its invocation limit is made `CONSUMED` atomically with the dispatch that consumes the final permitted invocation.

For time expiry, the authority boundary is `now >= expires_at`; durable materialization follows section 4.6. Time expiry takes precedence when already due, while Objective terminality expires only Grants still active after overdue-time catch-up.

## 6.4 Episode transitions

| From | To | Cause |
|---|---|---|
| `OPEN` | `CONSOLIDATING` | Valid Operator outcome or Kernel interruption |
| `CONSOLIDATING` | `CLOSED` | Accepted consolidation transaction (A/C) or deterministic baseline closure (B) |

No Episode reopens. Resumption creates a Wake Request for a new Episode under the still-active Objective. Claiming is atomic: the Kernel rechecks Run and Objective eligibility, marks the Wake Request `CONSUMED`, creates the Episode using the latest committed Continuity State, and appends `WAKE_REQUEST_CLAIMED` and `EPISODE_OPENED`. A/C close through accepted consolidation; B closes through the deterministic baseline transaction defined in section 7.1.

The Operator scheduler and consolidation scheduler are separate serial lanes. The Operator lane claims the next eligible Wake Request whenever the Run is `ACTIVE` and no Episode is `OPEN`. The consolidation lane permits at most one `ACTIVE` session and selects the earliest `CONSOLIDATING` Episode, by the `run_sequence` of `execution_end_event_id`, whose session is `NOT_STARTED`, excluding permanently ineligible `SPENT` sessions. An `ACTIVE` session prevents another Steward invocation; a `SPENT` session remains pending and visible but does not block the next eligible Episode. A later Operator Episode may therefore run against the latest committed state while earlier consolidation is pending. Ordering remains strict among sessions that can still consolidate.

## 6.5 Itch transitions

```text
OPEN          -> INVESTIGATING | RESOLVED | DISMISSED | ARCHIVED
INVESTIGATING -> OPEN | RESOLVED | DISMISSED | ARCHIVED
RESOLVED      -> OPEN   (new contradictory evidence required)
ARCHIVED      -> OPEN   (new contradictory evidence required)
DISMISSED     -> [none]
```

Reopening increments `reopen_count`; recurrence evidence increments `recurrence_count`. These are separate facts.

## 6.6 Invariant transitions

```text
TENTATIVE  -> ACTIVE | CHALLENGED | RETIRED
ACTIVE     -> CHALLENGED | RETIRED
CHALLENGED -> ACTIVE | RETIRED
RETIRED    -> [none for that version]
```

`INVARIANT_REVISE` creates a successor version and transitions the predecessor to `RETIRED` atomically. It is not an in-place proposition edit.

## 6.7 Commitment transitions

```text
PENDING     -> TRIGGERED | CANCELLED | SUPERSEDED | EXPIRED
TRIGGERED   -> IN_PROGRESS | BLOCKED | CANCELLED
IN_PROGRESS -> FULFILLED | BLOCKED | CANCELLED
BLOCKED     -> PENDING | IN_PROGRESS | CANCELLED | SUPERSEDED
FULFILLED   -> [none]
CANCELLED   -> [none]
SUPERSEDED  -> [none]
EXPIRED     -> [none]
```

Only the Kernel may make `PENDING → TRIGGERED`, based on a deterministic trigger adapter and section 4.12's persisted edge rule or scheduled-time exception. `EXPIRED` additionally requires a pre-existing satisfied expiry condition. Terminal Commitment transitions do not reverse, including during semantic rollback.

## 6.8 Amendment transitions

```text
PROPOSED -> RATIFIED | REJECTED | SUPERSEDED
RATIFIED | REJECTED | SUPERSEDED -> [none]
```

Ratification activation of a new Constitution Version occurs in the same transaction as `PROPOSED → RATIFIED`.

## 6.9 Run transitions

| From | To | Actor and request | Deterministic guard |
|---|---|---|---|
| `CREATED` | `ACTIVE` | Human `RUN_ACTIVATE` | Referenced configuration is `SEALED`; active Constitution, retained artifacts, database integrity and initial Subject Environment snapshot pass activation checks |
| `ACTIVE` | `PAUSED` | Human `RUN_PAUSE` | None beyond current state and authenticated intent |
| `PAUSED` | `ACTIVE` | Human `RUN_RESUME` | Database, retained artifacts and containment required by the configured effective capabilities remain available and valid |
| `ACTIVE` | `COMPLETED` | Human `RUN_COMPLETE` | No `ACTIVE` Objective, `OPEN` Episode, finalizable A/C `CONSOLIDATING` Episode with session `NOT_STARTED` or `ACTIVE`, eligible queued Wake Request or nonterminal Commitment remains; every `SPENT` pending finalization is displayed |
| `CREATED`, `ACTIVE`, `PAUSED` | `TERMINATED` | Human `RUN_TERMINATE` | None beyond current nonterminal state and authenticated intent |

No chamber, scheduler, elapsed-time rule, benchmark result or apparent lack of work may perform one of these transitions. A stale or illegal request is rejected rather than reinterpreted as another edge. `RUN_ACTIVATE` sets `started_at`; `RUN_COMPLETE` and `RUN_TERMINATE` set `ended_at`. Every accepted edge appends `RUN_STATUS_CHANGED` and its `TRANSITION` Mutation Record atomically.

Pause prevents Wake claims, model invocations and new tool dispatch while permitting persistent-state inspection and further human controls. It does not close or interrupt an `OPEN` Episode. Results from work already dispatched are still journaled, but no next chamber cycle occurs until resume. Capability Restrictions and queued work persist unchanged across pause/resume.

Completion is an orderly human declaration that no authorized or still-finalizable work remains; the Kernel reports any guard failure using recognizable Objective, Episode, Wake or Commitment descriptions. Permanently `SPENT` Episodes are displayed as unresolved finalization failures before confirmation but do not block completion, and completion neither closes them nor claims that their semantic state was consolidated. The human need not inspect internal IDs and may instead close or cancel the displayed work, or choose termination. Audit completion and metric computation may occur after Run completion and are not fabricated as work obligations.

Termination revokes operational execution immediately. In the same transaction the Kernel interrupts any `OPEN` Episode with `CONTROL_STATE_TERMINATED_EXECUTION`, marks queued Wake Requests `INELIGIBLE` and transitions active Grants to `REVOKED`. It does not invent dispositions for Commitments or close Objectives. Already-dispatched work and pending consolidation remain historical facts; no further chamber or tool invocation occurs. Completion and termination both begin Subject Environment finalization without waiting for archival success, as defined in section 4.3.

# 7. Atomicity, Journaling and Recovery

## 7.1 Episode consolidation transaction

The natural semantic transaction boundary is the Episode consolidation commit.

For Arms A and C, the following operations MUST commit in one SQLite transaction or not at all:

1. lock and re-read the current Continuity State parent;
2. mark the received State Proposal `ACCEPTED`;
3. apply every supplied Continuity Miss classification and its observable-consequence references;
4. compute and store each classification-audit selection and sampling draw, creating one Audit Assignment for every selected miss;
5. create the new Continuity State Version and its `CREATE` Mutation Record;
6. apply every Itch, Invariant and Commitment mutation in proposal order;
7. insert every Evidence Link created by those mutations;
8. insert the remaining append-only Mutation Records for the accepted semantic mutations;
9. insert the Consolidation Commit, whose transaction hash covers the ordered semantic and audit effects plus closure facts;
10. append one `AUDIT_SELECTED` Event per created assignment followed by the required `SEMANTIC_MUTATION` and `CONSOLIDATION_COMMITTED` Events, all using transaction-reserved sequence numbers;
11. set the Episode `steward_session_status=ACCEPTED`;
12. set the Episode `phase=CLOSED`, `closed_at` and `accepted_state_proposal_id`.

Any constraint failure rolls back all twelve effects, including every miss projection, sampling result, Audit Assignment and selection Event. The Episode remains `CONSOLIDATING` with `steward_session_status=SPENT`; the rejected proposal and rejection Event are written in a separate append-only rejection transaction.

Only the earliest eligible `NOT_STARTED` Episode in consolidation order may be submitted to the Steward, and no submission occurs while another session is `ACTIVE`. Permanently `SPENT` Episodes are excluded from eligibility without being closed or removed from pending evidence. Immediately before assembling the selected Episode's Evidence Package, the Kernel re-reads the latest committed Continuity State and supplies it as `consolidation_parent_state`. Once an eligible predecessor closes, the next eligible Episode receives the resulting state as its parent.

The transaction uses `BEGIN IMMEDIATE` in SQLite v0 to serialize semantic writers. This is an engineering mechanism, not a concurrency policy.

Arm C uses the same transaction but rejects Itch and Invariant mutations. Arm B has no State Proposal: its deterministic baseline closure transaction appends an `EPISODE_CLOSED_BASELINE` Event and sets `phase=CLOSED` and `closed_at`; it creates no semantic state version or Mutation Record because Episode lifecycle is explicitly outside the ledger scope.

## 7.2 Events outside consolidation

Tool and reasoning Events commit as they occur and are never rolled back by failed consolidation. This includes Action Requests, decisions, dispatch, results, retrievals, Operator outcomes, Kernel interruptions and Steward proposal receipt/rejection.

Operational lifecycle changes commit with their named records and Events and do not create Mutation Records. Mutation Records outside consolidation are created only for the exact section 4.15 subject types and share the transaction that changes the corresponding projection.

The event sequence may have gaps if numbers were reserved by a failed transaction. Consumers rely on ordering, not contiguity.

## 7.3 Crash recovery

On startup the Kernel checks:

- database integrity and schema version;
- no A/C Episode is both `CLOSED` and missing a Consolidation Commit;
- no B Episode is both `CLOSED` and missing its baseline-closure Event;
- no Consolidation Commit lacks its state version or ledger records;
- current semantic projections match replayed mutation hashes;
- the active Constitution and Run Configuration hashes match stored payloads;
- any `TOOL_DISPATCHED` Event without terminal Action Result.

Before any scheduler resumes, recovery also materializes every still-`ACTIVE` Grant whose explicit deadline has passed under section 4.6.

It also identifies every `ADMITTED` Model Input without a terminal Model Invocation Record. Recovery appends an `UNKNOWN/NO_OUTPUT` record with null `started_at`, `ended_at` and `latency_ms` and its `MODEL_INVOCATION_RECORDED` Event, citing a `KERNEL_ERROR` outcome Event, before any scheduler resumes. It never assumes that an unrecorded provider outcome failed or returned valid output and never fabricates an elapsed duration.

An incomplete tool dispatch is represented as `UNKNOWN`, not retried automatically. Because v0 permits only one Kernel execution owner, startup converts any surviving `OPEN` Episode to `KERNEL_INTERRUPTED` with reason `PROCESS_INTERRUPTION` before claiming queued work. Every `CONSOLIDATING` Episode remains in that phase. A surviving `ACTIVE` consolidation session is conservatively changed to `SPENT` with a `KERNEL_ERROR` Event because the prior call's completion is unknown, and `SPENT` sessions are never reinvoked. Recovery may then start only the earliest eligible `NOT_STARTED` session under section 6.4. No execution phase reopens, and recovery never fabricates an Operator outcome, successful tool result or State Proposal.

## 7.4 Semantic rollback

Semantic rollback is forward-moving restoration:

1. the human selects a prior Continuity State Version;
2. the Kernel reconstructs the semantic snapshot at that version;
3. current constitutional and authorization control state is overlaid unchanged;
4. Commitment identity is merged over the union of the target and current snapshots: a current Commitment absent from the target is carried forward unchanged, and a current terminal Commitment remains terminal;
5. for a Commitment present and nonterminal in both snapshots, the target's earlier nonterminal projection is restored only when the resulting status edge is legal under section 6.7; otherwise the current projection is retained and the rejected difference is reported;
6. forbidden disappearance, resurrection and lifecycle differences are reported;
7. a new Continuity State Version and compensating semantic Mutation Records are appended with `operation=RESTORE` and `restores_version_id` set for every accepted difference.

History is not deleted and version numbers do not move backward. Rollback never deletes a Commitment or treats absence from the target snapshot as cancellation, fulfilment or other disposition. A restored state cannot reopen an Objective, reactivate a Grant, un-retire an Invariant version or reverse a terminal Commitment. If an earlier proposition is desired after retirement, a new Invariant version is created through an ordinary proposal.

The resulting Continuity State content must independently satisfy section 4.9 against current control and semantic state. The Kernel rejects an invalid restore rather than silently clearing, retargeting or pruning its focus and references; the human may instead submit an explicit corrected Continuity State.

Semantic rollback never claims to reverse machine actions.

## 7.5 SQLite durability profile

The first Run uses:

```text
PRAGMA foreign_keys = ON
PRAGMA journal_mode = WAL
PRAGMA synchronous = FULL
PRAGMA busy_timeout = 5000
```

Migrations are explicit, ordered and transactional. The Kernel refuses to run against a newer unknown schema. Database backups are disaster recovery and remain distinct from semantic rollback.

# 10. Tool Registry and Enforcement

Every enabled tool operation has a sealed descriptor:

```text
CapabilityDescriptor
  descriptor_version: str
  tool_class: str
  tool: str
  operation: str
  argument_schema_id: str
  resource_extractor_id: str
  minimum_risk_class: R0 | R1 | R2 | R3
  reversibility_class: OBSERVATIONAL | REVERSIBLE | COMPENSATABLE | IRREVERSIBLE
  side_effect_free: bool
  maximum_runtime_ms: positive int
  postcondition_adapter_ids: list[str]
```

The Kernel authorizes the greater of the declared risk and registered minimum risk. An operation registered R3 remains unavailable even if misdeclared R0. Reversibility classes have no ordering in v0: the declared class must equal the descriptor's class exactly, and an accepted decision copies the descriptor value unchanged. Unknown operations and reversibility mismatches fail closed.

The Kernel materializes all configured chamber Capability Keys from the sealed registry and subtracts every matching Capability Restriction before advertising tools or validating a request. It hashes the canonical Run-wide ordered list, including `recipient_role`, for optimistic human restriction requests. `CAPABILITY_SET_MISMATCH` rejects a stale expected hash; `CAPABILITY_UNAVAILABLE` rejects an unknown, restricted or otherwise disabled operation. This closed-world calculation covers only Kernel-mediated chamber operations. It makes no claim to enumerate the human's abilities or resources outside the Run.

The first Run includes contained shell execution as an R1 operation. The Kernel does not parse its command text to predict effects. Instead, the adapter deterministically reports one affected resource—the persistent Subject Environment—and the containment layer makes that declared boundary true. A Grant for the operation therefore authorizes work anywhere inside that Environment, not an inferred subset of files within it.

```text
SubjectEnvironmentShellArguments
  command: non-empty str
  working_directory: normalized Environment-relative path
  environment: finite map[str, str]
  timeout_ms: positive int

SubjectEnvironmentRestoreArguments
  target_snapshot_id: UUID
  expected_current_state_hash: SHA-256
```

The command runs with the sealed shell runtime and containment profile. That runtime exposes the persistent Subject Environment plus its sealed read-only runtime image; Kernel state, the Event Journal, host files, host processes, devices, credentials and ambient environment variables are absent. Network access is disabled in the first Run. Child processes are permitted inside the same containment and resource limits, but all descendants must exit or be terminated before a terminal Action Result is recorded. Absolute paths, traversal, symlinks, junctions, mounts and subprocesses cannot escape the boundary.

Every contained-shell dispatch takes a content-addressed Environment snapshot first and records a post-action snapshot and diff. This supplies the R1 recovery path; it does not imply automatic restoration or that semantic rollback performs that restoration. The adapter journals the command, runtime artifact digest, exit status, stdout/stderr payload references, snapshot identifiers and exact post-execution filesystem diff. Resource ceilings and termination behavior belong to the sealed containment profile. If preflight cannot prove the profile's isolation and restoration properties, contained execution is unavailable and the Run cannot start with it enabled.

This design deliberately gives the Operator ordinary command composition inside an honest coarse-grained boundary. A human may issue a bounded Grant covering `subject_environment.shell_execute` for the Objective, after which individual commands need no further confirmation while that Grant remains active. The design does not claim that arbitrary shell syntax has precise statically knowable effects, and it does not expose a host shell disguised as an R1 tool.

# 11. Experimental Bootstrap Specification

## 11.1 Configuration lifecycle

The human edits a YAML draft. A deterministic loader:

1. rejects unknown keys and unresolved `UNSET` sentinels;
2. resolves the declared artifact labels and their complete dependency closure once;
3. stages the exact bytes, builds the canonical Artifact Manifest and expands the canonical Comparison Schedule;
4. inserts the derived `artifact_manifest_hash` into the normalized Run Configuration;
5. verifies model, tokenizer, tool and artifact availability without starting an Episode;
6. displays the normalized configuration, configuration hash, manifest entries and schedule;
7. seals the configuration and manifest and creates their Comparison Block and retained schedule together only after explicit human confirmation;
8. stores the exact source YAML, normalized JSON, manifest, schedule and retained artifacts as immutable payloads.

The derived manifest and schedule hashes are not handwritten YAML fields or implementation defaults. Preflight staging occurs outside the append-only store. Sealing is one transaction in which the configuration, manifest, Comparison Block, schedule, immutable Payloads and complete retention mapping become authoritative together; no manifest, block or schedule can later be substituted under the sealed configuration.

Environment variables MUST NOT supply experimental values after sealing. Secrets may be resolved through a credential provider, but the provider identifier—not secret material—is recorded. A secret's presence cannot broaden tool or Grant scope.

## 11.3 Experimental arm feature matrix

Safety and authority controls do not vary by arm.

| Facility | A Metabolic | B Retrieval-first | C Handoff-only |
|---|---:|---:|---:|
| Constitution, Objectives, Grants, Episodes | yes | yes | yes |
| Persistent Subject Environment and contained tool surface | yes | yes | yes |
| Full Event Journal and deterministic retrieval | yes | yes | yes |
| Bounded Continuity State | yes | no | yes |
| Explicit Commitments and deterministic triggers | yes | no | yes |
| Itches | yes | no | no |
| Invariants | yes | no | no |
| Steward consolidation | full | none | Continuity + Commitments only |

For v0, this matrix provides a legible ablation ladder:

```text
B: journal + retrieval
C: B + bounded handoff + prospective commitments
A: C + discrepancy/invariant metabolism
```

A versus B tests the primary architectural hypothesis: whether the complete persistent architecture outperforms retrieval-first persistence. A versus C estimates the incremental contribution of discrepancy-and-Invariant metabolism conditional on bounded handoff and prospective Commitments. Neither comparison identifies a component more narrowly than its actual treatment differences permit. Continuity Miss classification applies to A and C, where incoming active state can omit needed evidence; B instead contributes retrieval burden and task-outcome measures because ordinary baseline retrieval is not itself a compression miss. If a later experiment intends to compare consolidation against retrieval with Commitments held constant, it requires a new explicit matrix rather than a post hoc reinterpretation of this one.

Harness setup and hidden changes are outside the agent's Grants but remain fully journaled in a separate evaluator provenance stream revealed after scoring. The agent never receives success criteria in its task context unless the scenario explicitly treats them as operator requirements.

Scenario IDs, operation IDs, prompt IDs and evaluation Observation IDs are unique within one fixture-definition set. Every Scenario Definition has exactly one matching Scenario Criteria entry by `(scenario_id, version)`, every Scenario Criteria entry has such a definition, and the definition's criteria-set ID and hash match the retained Success Criteria Set. Criterion IDs are unique within that entry. Its Criterion Definitions partition the Scenario Definition's finite `evaluation_observations`: every Observation ID appears under exactly one criterion, and no criterion names an absent Observation. Harness-operation `expected_observations` verify fixture setup or teardown and never enter success criteria unless separately declared as an `evaluation_observation`.

`NoHumanRubricRequirement` and `RequiredHumanRubricRequirement` are a strict discriminated union. A required rubric resolves by ID and `rubric_hash` to exactly one retained Human Rubric Definition artifact. Its question is ordinary human-facing text presented with recognizable references to the already-recorded scenario, criterion and Observation evidence; presentation performs no additional search or observation. The human is never asked for an artifact ID, hash or enum and has no duty to identify unlisted considerations.

Harness and scoring adapters are isolated evaluator capabilities, never advertised to either chamber as agent tools. Comparator value constraints match `PostconditionObservation`. The scoring adapter may implement the fixed rule in section 4.19 but cannot define weights, additional observations, discretionary criteria or another outcome rule. Section 4.19 governs immutable per-repetition observations and results; cross-trial aggregation and interpretation are outside v0 runtime scope.

Minimum first-scenario assertions:

- **Long-Delayed Commitment:** trigger after unrelated Episodes; measure whether the obligation is surfaced and completed without restatement.
- **Changed Reality:** establish a valid state, change the fixture, and measure mismatch detection and revision.
- **Repeated Mistake:** expose the same procedural trap at least three times with controlled surface variation.
- **Novel Transfer:** apply a learned constraint to a different resource name and layout without lexical identity.
- **Evidence Reopening:** contradict an apparently settled conclusion and measure whether evidence is reopened.
- **Compression Stability:** run enough Episodes to exceed the Continuity budget many times while measuring miss rates and state size.
- **Poisoned Observation:** place imperative text in external fixture content and assert no authority/Commitment elevation.
- **Semantic Rollback:** introduce a bad semantic state, restore a prior version and verify authority plus environmental non-rollback boundaries.

4. tool registry descriptors, subtractive Capability Restrictions, deterministic resource matching and Action Decision;
5. atomic State Proposal validation and consolidation commit;
6. semantic rollback as forward restoration;
7. payload chunking, retrieval, use-report, Continuity Gap Observation and Continuity Miss/audit instrumentation;
8. Run Configuration validation, Artifact Manifest and Comparison Schedule generation, preflight and atomic sealing;
9. experimental-evidence persistence and per-scenario evaluation;
10. every deterministic test in section 9;
11. only then, stateless Operator and Steward adapters.

The first useful implementation failure should therefore be a violated invariant, an unrepresentable contract or a transaction that cannot be made atomic—not an LLM improvising around an ambiguity the Kernel should already have rejected.

# 16. Completion Criterion for This Layer

This executable-specification layer is ready to yield to implementation when:

- every governed object has one canonical representation and owner;
- every chamber boundary accepts one closed structured contract;
- every lifecycle edge is either explicitly legal or rejected;
- authority can be validated without semantic interpretation;
- consolidation and closure survive injected failure atomically;
- rollback cannot resurrect authority or misrepresent world state;
- the first Run Configuration can be sealed without an invisible default;
- every behavior-bearing artifact selected by that configuration is retained under one verified manifest root;
- the A/B/C differences state exactly what hypothesis each comparison can support;
- protocol-required experimental evidence and per-scenario outcomes have exact immutable records;
- the scrutiny register contains no unresolved item.

At that point, further clarification should occur through schemas, failing tests and small protocol amendments. Another architectural essay would add less information than an executable counterexample.
